# Asset library

Everything in the library is **derived, never hand-indexed** — `get_assets`
computes it per request:

- **Scenes** — the images reel.yaml's `stills:` map actually anchors on. Each
  carries `still:<name>` plus `used_by:<scene>` for every scene that
  references it, so a still's downstream is always visible.
- **Characters** — two pools per character:
  `characters/<slug>/references/` (the operator's uploaded base images —
  the source `characters.attributes` are pulled from) and
  `characters/<slug>/posed_stills/` (generated reference stills, one
  character / one pose / blank backdrop per image). Legacy flat files in
  `characters/<slug>/` still index — flat `_refNN`/`_sheetNN` files read as
  posed, anything else as reference. Labels: `char:<slug>`, `pose:<file>`,
  plus `reference` or `posed` (the pool side). Update a pool and every
  label that names it updates with it.
- **Backgrounds** — location pools under `backgrounds/<location>/` (one pool
  per `locations:` entry, modeled exactly like characters), labelled
  `loc:<location>` and `background`. Generated by `reel.py bg <location>`
  (10 seed/prompt variants per run).
- **Custom** — anything the operator drops into `images/`.
- **LORA / Theme** — `themes/<slug>.yaml` descriptors (`slug`, `lora`,
  `trigger`, `labels`).
- **Audio** — rendered music segments plus anything under `audio/`.

`assets.yaml` in the workspace attaches extra labels to any asset (keys are
workspace-relative, or bare filenames for stills in `still_dir`):

```yaml
labels:
  characters/fox_boy/run_.png: [hero, main-walk]
  tony_catch_00006_.png: [char:tony, cond:were-tiger, scene:s5_skydunk]
```

Labels are typed free-form: `char:<slug>` (character), `scene:<slug>`
(foreign key to a scene id), `cond:<x>` (human, were-tiger, …), `ref` (the
pick `char_ref`/`plate_ref` resolve), `job:<id>` (provenance), or any other
tag. The studio's inspector writes them; you set them with
`update_asset_labels` — never by hand-editing assets.yaml.

Generated images are born `non-verified` and labelled per-file THE MOMENT
they land (reel.py labels each file as it lands — a killed run leaves no
unlabelled orphans). The operator approves (✓ — the label is removed) or
deletes (✕ — the file is gone) on the thumbnail or in the inspector; only
non-verified assets are deletable. When the operator asks you to clean up a
generation run, remove
the `non-verified` label on the keepers with `update_asset_labels` — deletion
is their ✕, not an edit.

## Approval is inviolable

- A ✓-approved or operator-kept asset is NEVER deleted, overwritten, moved
  or cleared by any regen — not by the agent, not by a driver script, not
  by the pipeline. Runs only ADD files.
- Every round writes fresh names (seed+timestamp-stamped prefixes), so a
  regen cannot collide with, silently replace, or re-thumbnail an approved
  file. If a cache collision is even suspect, stop and verify against the
  file's mtime and embedded prompt (`get_provenance`).
- Clearing a pool happens ONLY on the operator's explicit words, after
  their picks are recorded (`seeds:` ladder / labels).
- REVIEW RESULTS: after every run, look at the produced images (`view_image`)
  against the operator's standing feedback BEFORE reporting. A report
  without review is the failure mode — never hand over unreviewed pixels.

Because labels name pools and scenes rather than individual files, refreshing
a character pool and re-deriving is the same operation for you as for a
human: read the labels, regenerate what points at them.

## Extraction: photos -> attributes (pull, then layer corrections)

When a character's `characters.<slug>.attributes:` is missing or the operator
asks to (re)extract: `view_image` each image in `characters/<slug>/references/`
— LOOK, one by one, at the MAIN FOCUS character — and write the attribute map
with `update_yaml`:

```yaml
characters:
  <slug>:
    attributes:
      hair: …          # color + style (use the operator's own words)
      skin: …
      eyes: …          # color + state (e.g. half-lidded)
      clothing: …      # every worn layer + notable details
      accessories: …
      stance: …        # posture, weight, default attitude
      expression: …
      negatives: …     # things the GENERATION must not render (e.g. shirt
                       # under the bandages) — excluded from the positive
                       # prompt and routed to the negative input; at cfg 1
                       # it is informative only, so the POSITIVE clothing
                       # text must simply never mention the excluded thing
```

Rules: describe what you SEE in positive terms; exclusions live in the
`negatives:` key and the positive text omits the concept entirely. THE
NEGATIVE CHANNEL SUBTRACTS: `attributes.negatives` is a list of bare
concept words ("undercut, bandaged mouth") — the engine removes exactly
those concepts. NEVER write "no X" in a negative (the "no" would
condition X INTO existence). Feedback
overwrites the pulled info (operator's words replace yours
in the keys, never the reverse); the downstream prompts are composed from
these keys automatically — one key edit restyles every future still.

## Rules

1. Anchor scenes with `still:<name>` refs into named library stills — never
   literal paths into `still_dir` when a named still exists.
2. A still that `get_project` shows `present: false` is a broken anchor:
   the file is missing from the pipeline's output dir.
3. New stills come from the wired Qwen generators: `generate kind=still
   slug=<location>` renders a background plate into `backgrounds/<location>/`;
   `generate kind=sheet slug=<character>` renders reference stills
   (TEXT-driven from the yaml `characters:` block — attributes + variants +
   backdrop; the pool images are NEVER fed to the model) into
   `characters/<slug>/posed_stills/`; `generate kind=image_edit name=<shot>`
   renders a `shots:` entry's anchor stills (10 variants each) into the
   stills dir. Point `stills:` at the variant the operator picks. The pool
   member tagged `ref` in `assets.yaml` is the identity every shot uses.
4. Every generated file carries its provenance: a `job:<id>` label
   (images) or manifest `job` field (videos, music) linking to the
   journaled job record. `get_provenance path=<asset path>` returns the
   whole claw-back — request args, seed, and for images the exact prompt
   and models embedded in the PNG. Never re-derive a prompt by guessing:
   read it from provenance.
